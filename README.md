# Katamari Web

괴혼(塊魂) 웹 구현. Three.js + TypeScript. 물리엔진 없음.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # tsc --noEmit && vite build
```

조작: `WASD` 이동 · `Shift` 대시 · `R` 리셋 · `T` 계측 · `M` 음소거

맵은 셋이다 — 원작 **타케다 저택 1층**, **피죤타운**, **어친타운**. 여덟 판이
이 셋을 돌려 쓴다. 열면 **스테이지 선택 화면**이 먼저 뜨고, 1을 깨야 2가 열린다.

## 안 열릴 때

`npm run dev` 가 안 되면 프로덕션 빌드로 우회할 수 있다:

```bash
npm run build
npx vite preview --port 4173
```

`lsof -i :5173` 에 `IPv6` 만 뜨면 IPv4 바인딩 문제다 (vite.config 에서 해결됨).



브라우저 콘솔에 `[boot]` 로그가 단계별로 찍힌다. 어디서 멈췄는지 바로 보인다.

```
[boot] 시작 599ms
[boot] 지형 로드 (건물 369채) 681ms
[boot] Game 생성 992ms
[boot] 첫 프레임 1142ms
```

부팅 중 예외가 나면 **화면에 스택 트레이스가 뜬다.** 빈 화면이 나오면 안 된다.

범위 좁히기:

| URL | 확인하는 것 |
|---|---|
| `?nocity=1` | 지형을 빼고 띄운다. 이걸로 되면 지형 데이터 문제 |
| `?stage=star2` | 선택 화면을 건너뛰고 그 판으로 직행 (`star1` ~ `star8`) |
| `?district=jamsil` | OSM 실측 도시로 전환 — 보조 모드 |

`?stage`가 **없으면 선택 화면**이다. 있으면 곧장 그 판으로 들어간다 —
도구·e2e·판 전환이 전부 이 문으로 들어온다.

### 헤드리스 스크린샷

```bash
npm run shot -- "http://127.0.0.1:5173/?district=house&stage=star1" out.png 26000
```

`--virtual-time-budget` 방식은 **이 게임에서 안 끝난다.** 헤드리스에는 컴포지터가
없어서 `requestAnimationFrame`이 한 번 돌고 멈추고, 그러면 가상시간도 안 흐른다.
그래서 CDP로 직접 붙어 **캡처를 반복해 프레임을 강제**한다 — 캡처 한 번이
컴포지트 한 번이고 그게 rAF를 펌프한다. `WARMUP=40` 으로 굴릴 프레임 수를 정한다.

swiftshader라 부팅에 20~30초 걸린다. 실제 GPU에서는 1초대다.

웹폰트는 쓰지 않는다. CSS `@import` 로 외부 폰트를 부르면 그 요청이
렌더링을 막아서, 네트워크가 느린 환경에서 페이지가 통째로 안 열린다.
게임에 폰트 하나 때문에 그런 위험을 둘 이유가 없다.

## 핵심 5가지

1. **콜라이더는 끝까지 구(球)다.** 붙은 물체는 충돌 형상에 영향을 주지 않는다.
   울퉁불퉁해 보이는 건 메시가 밖으로 삐져나와 생기는 착시. 원작도 이 방식이다.
2. **흡수 = 리페어런팅.** `Object3D.attach()`가 월드 트랜스폼을 보존하며 부모를 갈아끼운다.
   이후 구르기는 자식들이 알아서 따라온다.
3. **위치 노드 / 회전 노드 분리.** `pivot`(이동) → `group`(회전) → 코어 + 붙은 것들.
   구르기는 `quaternion.premultiply()`로 월드 기준 누적.
4. **카메라 거리를 반지름에 비례시킨다.** 성장의 쾌감은 공이 커지는 게 아니라
   세상이 작아지는 것에서 나온다.
5. **표면 패킹.** 붙은 물체끼리 겹치지 않게 구면 위에서 밀어낸다.
   이게 없으면 같은 자리에 겹쳐 박혀서 공이 그냥 커지기만 한다.

## 스테이지 — 저택·피죤타운·어친타운

원작 塊魂(2004)은 한 맵을 계속 굴리는 게 아니라 **스테이지가 여러 개**다.
각각 목표 크기와 제한시간이 있고, 끝나면 왕이 평가한다.

**원작은 큰 맵이 셋(House / Town / World)이고 그 안에 구역이 있다.** Roadway는
World가 아니라 **Town 구역**이고, Urchin Town은 **World 구역**이다. 그래서 8번은
새 맵이 아니라 동네를 재사용하고, 6·7번이 World를 쓴다.

| `?stage=` | 이름 | 목표 | 제한시간 | 시작 | 구역 |
|---|---|---|---|---|---|
| `star1` | 별을 만들어라 1 | 10cm | 없음 | 5cm | **거실 한 칸** |
| `star2` | 별을 만들어라 2 | 20cm | 6분 | 5cm | 저택 전체 |
| `star3` | 별을 만들어라 3 | 50cm | **9분** | 5cm | **동네 (Pigeon Town)** |
| `star4` | 별을 만들어라 4 | **1m** | 10분 | 5cm | 저택 전체 |
| `star5` | 별을 만들어라 5 | **2m 70cm** | 13분 | 5cm | 동네 (Pigeon Town) |
| `star6` | 별을 만들어라 6 | **3m** | 11분 | **50cm** | **어친타운 (World)** |
| `star7` | 별을 만들어라 7 | **6m** | 10분 | **50cm** | 어친타운 (World) |
| `star8` | 별을 만들어라 8 | **12m** | **18분** | **10cm** | 동네 (Roadway) |

1번에 시계가 없는 것도 원작 그대로다 — 조작을 배우는 판이다.

> **확증도가 낮은 것 셋. 지어낸 게 아니라 모르는 것이다.**
> - **6번의 무대**를 명시한 자료를 못 찾았다. 선물 위치가 "주유소 뒤 교정,
>   정글짐 옆"인데 그건 어친타운의 특징(양 끝의 공원과 학교)이라 World로 잡았다.
>   **추정이다.**
> - **6번 제한시간**이 자료마다 10분/11분으로 엇갈렸다. 더 구체적인 쪽을 택했다.
> - **시작 크기는 1·6·7·8번만 확인됐다.** 2~5번은 어느 자료에도 없어서 1번 값
>   (5cm)을 그대로 뒀다.

**1번은 거실 한 칸이고, 문이 아예 없다.** 원작 「별을 만들어라 1」에는 다른 구역이
없다. 그래서 문턱을 올려 잠그는 게 아니라 벽 네 장과 기둥 네 개만 세운다 — 게이트가
0개라 `City.openGates()`가 첫 줄에서 빠져나오고 왕의 개방 대사도 안 뜬다.
갈 수도 없는 방 여섯 개에 물건 1,050개를 깔 이유가 없다 (거실 전용은 430개).

**저택이 열리는 건 2번부터다.** 2번이 다시 5cm에서 시작해 집을 처음부터 여는 것도
원작 그대로다 — 같은 맵을 목표만 키워 다시 굴리는 게 이 게임의 구조다.
아래 개방 표는 그래서 **2번 이후 기준**이다.

### 진행 — 선택 화면과 해금

원작은 왕의 방에서 별을 고르고 지구로 내려간다. 그 구조만 가져왔다.

- **`?stage`가 없으면 선택 화면부터.** 지형 로드보다 먼저 분기하므로,
  고르기만 할 화면에 잠실 2.9MB를 받지 않는다.
- **깬 만큼 열린다.** 1을 깨야 2가, 2를 깨야 3이 열린다.
  진행도는 `localStorage['katamari.cleared']`에 id 배열로 남는다.
- **깨면 결과 카드에서 바로 이어간다.** 「다음 별로」·「다시」·「스테이지 선택」.
  「다음 별로」는 **클리어했을 때만** 뜬다 — 시간이 다 됐는데도 이어갈 수 있으면
  제한시간이 아무 의미가 없다. 마지막 판(star8)에서도 안 뜬다.

**잠금은 선택 화면의 규칙이지 실행 금지가 아니다.** `?stage=star3`으로 직접
들어오면 그대로 실행된다 — 도구·e2e·디버그가 쓰는 뒷문이라 막지 않는다.

판 전환은 **리로드**다. `Game`은 생성자에서 월드를 통째로 만들지만 `stop()`은
입력·자막만 거둔다(렌더러도 GPU 버퍼도 안 놓는다). 판마다 `new Game`을 하면
누수라, URL을 갈고 다시 부팅하는 쪽이 정확하다.

`localStorage`는 프라이빗 모드·쿠키 차단에서 **읽기만 해도 던진다.** 전부 감싸고,
실패하면 "아무것도 못 깼다"로 돌아간다 — 저장이 막혔다고 게임이 안 뜨면 더 나쁘다.

### 집 구조 (1층)

```
        ┌──── 뒷마당 8×6 ────┐   ← 10cm 개방
 ┌──────┼─────┬──────┬──────┐
 │ 부엌 │ 복도 1.8×6.3│화장실│
 │      ├─────┴──┐   │      │
 │      │아이 방 │   └──────┘
 └──────┼────────┴───────┐
        │  거실 5.4×4.5   │  ★ 스폰
        └───── 툇마루 ────┘
```

**구역은 문이 아니라 크기로 열린다** (아래는 **별을 만들어라 2 이후** 기준이다 —
1번에는 문이 아예 없다). 원작이 그렇다 — 뒷마당은 지름 10cm,
마루 밑은 20cm에 들어갈 수 있다.

| 문 | 개방 지름 |
|---|---|
| 거실 → 복도 | 6cm |
| 복도 → 아이 방 · 부엌 · 화장실 | 8cm |
| 툇마루 → 뒷마당 | **10cm (원작 값)** |

**게이트는 새로운 물체 종류가 아니라 그냥 건물이다.** `CityBuilding.gate`에 지름
문턱을 적어두면 `City.openGates()`가 그때 지워버린다. 충돌·렌더가 기존 건물 경로를
그대로 타므로 새 충돌 코드가 한 줄도 필요 없다.

> **불변식: `gate < size / pickRatio`.**
> 어기면 문이 열리기 전에 플레이어가 문을 먹어치운다.
> 문짝 폭 최소 0.6m라 size가 최소 1.8m(문 높이)이고, 최대 개방값 0.10m는
> 1.8 / 0.85 = 2.12m보다 한참 작다.

**벽을 잘라내고 그 자리에 문을 세운다.** 벽 위에 덧대면 문이 사라져도 뒤에 벽이 남는다.
`wallWithDoor()`는 문이 벽 구간을 벗어나면 **즉시 throw** 한다 — 실제로 부엌·화장실을
복도 z구간 밖에 두는 바람에 8cm에서 집 밖으로 나갈 수 있었고, **화면으로는 전혀
보이지 않던 결함**이었다. 스폰에서 flood fill 하는 도달 범위 검사가 잡았다.

### 동네 맵 — Pigeon Town

원작 「별을 만들어라 3」의 무대다. 원작 구조는 북쪽 언덕 위 **북 피죤타운**,
언덕을 내려오는 **상점가**, 마을을 관통하는 **메추라기 강**, 가운데 **도브 호수**와
그 안의 섬, 호수를 도는 도로, **참새 언덕**, 한 모서리의 **캠프장**과 이웃한 **공사장**.

**평면 투영이다.** 언덕·강 깊이·미끄럼틀은 못 만든다(「알려진 한계」). 높이차로
나뉘던 구역을 크기 게이트로 나눠 평면에 폈다.

```
        ┌──── 북 피죤타운 (주택 5채·가로수) ────┐  25cm
        └───────────┬──────────────────────────┘
   ┌─────────┐      │ 상점가 (상점 4채·자판기)      18cm
   │ 공사장   │◀─────┤                    35cm
   └─────────┘      │
                ★ 시작 마당 (개집)
                    │ 흙길                          8cm
   ┌─────────┐      │
   │ 캠프장   │◀─ 비둘기 광장 ─▶ 호숫가 도로        12 / 20 / 30cm
   └────┬────┘          │                    │
        │           도브 호수 ─ 다리 ─ 섬      │      45cm
        ▼                                    ▼
   메추라기 강 (6m)                       야구장 (4m)
                                              │
                                         참새 언덕 (8m)
```

**바깥 세 구역은 별을 만들어라 8(12m) 전용이다.** 안쪽 아홉 구역은 짧은 변이
9m라 12m 공이 아예 안 들어간다. 야구장·메추라기 강·참새 언덕은 짧은 변이
28·22·32m다 — 셋 다 원작 Town에 있는 구역이다.

| 문 | 개방 지름 |
|---|---|
| 마당 → 흙길 | 8cm |
| 흙길 → 비둘기 광장 | 12cm |
| 마당 → 상점가 | 18cm |
| 광장 → 호숫가 도로 | 20cm |
| 상점가 → 북 피죤타운 | 25cm |
| 광장 → 캠프장 | 30cm |
| 상점가 → 공사장 | 35cm |
| 호숫가 → 섬 (다리) | 45cm |
| 호숫가 → 야구장 | **4m** |
| 캠프장 → 메추라기 강 | **6m** |
| 야구장 → 참새 언덕 | **8m** |

> **이 열한 개는 원작 값이 아니라 설계값이다.** 원작 동네의 개방 크기를 명시한
> 자료를 못 찾았다. 집 맵의 뒷마당 10cm는 원작 값이라 그건 그대로 뒀다.

**문 폭은 개방 지름 × 1.25다.** 바깥 세 문을 2.4m로 뒀더니 4m에 열리는 야구장
문을 4m 공이 못 지나갔다. 문턱만큼 커진 공이 그 문을 통과해야 한다 — 25%는
조향 여유다. 정확히 지름만 한 구멍은 직진으로만 통과된다.

### 담장도 사라진다 — 문만 열어서는 안 된다

**문이 열려도 담장이 남으면 통로 폭은 문 폭 그대로다.** 그래서 공이 1.5m부터
시작 마당에 갇혔고, 6m가 넘으면 **한 칸도 못 움직였다.** 담장·문을 전부 지운
세계에서 재봤더니 12m 공도 38,742칸을 돌았다 — **막던 건 건물이 아니라 담장이었다.**
`curve`가 벽을 세지 않아서 여태 안 드러났고, 별을 만들어라 5(2m70cm)도 실제로는
굴러다닐 수 없는 상태였다.

`dissolveWalls()`(`stage.kit.ts`)가 구역을 나누는 담장에 **소멸 문턱**을 박는다:

```
소멸 지름 = max(가장 넓은 안쪽 문 폭, 이웃 구역 개방값 × 1.25)
```

자기 문보다 커진 공 앞에서 담장은 할 일이 끝난다. 그때 사라진다.

- **맵 테두리는 예외다.** 양옆 중 한쪽이 구역 bbox 밖인 벽은 끝까지 남긴다.
  처음엔 "한쪽이 구역 밖이면 테두리"로 봤는데 구역 사이의 **빈 땅**도 구역 밖이라
  시작 마당 담장이 안 사라졌다. 빈 땅은 맵 안이다.
- **자기 크기에 먼저 먹히는 벽에는 안 단다.** `gate < size / pickRatio` 를 못
  지키는 벽은 문턱보다 먼저 흡수돼 사라진다 — 게이트를 달면 불변식만 깨진다.
- **`boundary()` 로 테두리를 봉인한다.** 담장이 사라지고 나면 테두리에 벽이 없는
  구간으로 새어 나간다(어친타운에서 3m 공이 8,751칸 밖으로 나갔다). 구역 전체를
  감싸는 벽 네 장을 두른다. 길이가 곧 `size` 라 어떤 크기에도 안 먹힌다.

**공유 경계는 한 번만 세운다.** 바깥 구역을 붙이면서 호숫가·공사장·캠프장이 각자
자기 벽을 세워 새 게이트 위에 한 겹이 더 얹혔다 — 문이 열려도 안 뚫렸다.
각 변의 담당을 소스 주석에 못 박아뒀다.

**랜드마크 5채(7.5·8.8·10.4·12.2·14.0m)가 6.4m 위를 잇는다.** 안쪽 최대 흡수
건물이 주택 6.4m라 7.5m에서 먹을 게 없어진다. **원작 Town에 이런 건물이 있다는
뜻이 아니다** — 사다리를 위해 세운 것이다. 바닥면적을 작게 잡은 건 `size` 가
가로·세로·높이 중 **최대**라 넓적하면 폭이 크기가 되기 때문이다.

**끝까지 못 먹는 건 소품이 아니라 건물이다.** 목표 50cm면 `pickRatio 0.85`로
최대 42cm까지 먹는다. 자판기(1.8m)·상점(5m)·주택(6m)·가로수(3m)는 `CityBuilding`이다.
(별을 만들어라 5는 목표가 2m70cm라 이것들 일부를 실제로 먹는다 — 아래 「거리 집기」 참고.)
덕분에 소품이 전부 1cm~1.2m 안에 들어가고 **라벨 버킷 경계를 안 건드린다** —
이 값을 건드렸다가 잠실 사다리가 끊긴 전례가 있다.

**호수는 연석으로 둘러야 한다.** `CityData.water`는 배치 금지 구역일 뿐 **충돌이 없다.**
안 막으면 공이 수면 위를 굴러 지나가고 섬 게이트가 무의미해진다. 처음엔 연석에
게이트만 냈는데, 열리는 순간 호수 전체가 열렸다(도달 검사가 45cm에서 수면 5,109칸을
잡았다). **다리는 구멍이 아니라 상판이다** — 통로 양옆에 연석을 세우고 수면을
섬·통로를 뺀 다섯 토막으로 나눴다.

**거리 집기 23채가 1.2~2.7m를 메운다.** 소품은 1.2m에서 끊기고 그다음 건물이 1.8m였다.
`pickRatio 0.85`면 1.8m를 먹는 데 지름 2.12m가 필요한데 그 사이를 채우는 게 개집 한 채뿐이라,
별을 만들어라 5(2m70cm)의 마지막 구간이 121초를 잡아먹었다. 우체통·벤치·분수대·자전거·
전봇대·가로등·정자·게시판 같은 것들을 그 구간에 넣어 **이웃 크기 비를 1.09**까지 낮췄다
(`1/pickRatio` = 1.176 아래여야 그 자리에서 성장이 안 멈춘다).

> **도구가 게임과 다른 월드를 재고 있었다.** 집기를 12채 넣었는데 `curve` 곡선이
> **1초도 안 움직였다** — 그 도구가 소품만 굴리고 건물을 안 세고 있었다.
> `Game.resolveCity()`는 건물을 먹는다. 집 맵은 먹을 건물이 0채라 여태 안 드러났고,
> 동네가 생기며 나왔다. 지금은 `curve`도 건물을 센다(벽·문 제외).

**맵 크기가 곧 난이도다.** 처음 만든 동네는 1,800m²에 3,040개(1.7개/m²)였는데,
집 맵은 120m²에 1,480개(12개/m²)다. 7배 성기니 이동 시간이 성장을 지배해서
50cm 도달이 204초였다 — 탐욕 시뮬 기준이라 실제는 3~5배 느리고, 그러면 9분을 넘긴다.
**개수를 40% 올려도 3초밖에 안 줄었다.** 면적을 45%로 줄이자 104초가 됐다.
개수가 아니라 넓이였다.

### 어친타운 (World) — 별을 만들어라 6·7

원작 World 맵의 **Urchin Town** 하나만 만들었다. 나머지 열세 구역(파라다이스·
고래 도시·큰바다…)은 없다.

```
        ┌──── 학교 (교정·정글짐) ────┐  2.2m
        └──────────┬────────────────┘
   ┌────────┐      │ 큰길                 0.9m
   │ 주유소  │◀─────┤                1.2m
   └────────┘  ★ 시작 광장 (50cm에서 시작)
                    │ 상가                 1.6m
   ┌────────┐      │
   │  공원   │◀─ 교차로 ─▶ 부두          1.0 / 0.7 / 3.0m
   └────────┘
```

구역 8개 · 문 7개. **개방 문턱도 문 폭도 설계값이다** — 원작 값을 못 찾았다.

**공이 50cm에서 시작해 6m까지 간다.** 그 크기대의 물건은 집·동네 표에 없어서
World 전용 형태 12종을 새로 만들었다: 자전거·오토바이·자판기·우체통·표지판·
드럼통·벤치·그네·미끄럼틀·사람·승용차·가로수.

> **어친타운 소품이 집 물건처럼 보인다.** 표의 앞 다섯 버킷이 집·동네 형태를
> 재사용해서, 50cm로 시작하면 광장에 의자·스툴·주전자·물뿌리개가 깔린다.
> 원작 塊魂도 실외에 살림살이가 굴러다니긴 하지만 거리 스케일이라면 표지판·
> 화분 쪽이 더 맞다. **아직 안 고쳤다.**

### 라벨 표는 스테이지가 갖는다

```ts
placement: { rooms: TOWN_ROOMS, labels: TOWN_TABLE }
```

없으면 집 물건(`HOUSE_TABLE`)을 쓴다. 표는 이름 목록만이 아니라 **크기 경계까지**
들고 있다:

```ts
interface LabelTable { buckets: string[][]; min: number; max: number }
```

- 집·동네: `0.01 ~ 1.2m` — 버킷 개수와 경계가 같고 **이름만 다르다.**
  라벨은 물건의 정체고 경계는 사다리라, 경계까지 맵마다 바꾸면 `ladder` 가
  맵마다 다른 자를 대게 된다.
- 어친타운: `0.05 ~ 4m` — 공이 50cm에서 시작하므로 경계를 옮겨야 한다.
  1.2m 고정 경계로는 소품 절반이 마지막 버킷에 뭉쳐 **전부 「고양이·의자·스툴」**이
  된다.

절반은 기존 형태를 그대로 쓴다(개미·클립·화분·고양이…). 마당에 있어도 어색하지
않은 것들이다.

### 세계관 — 왕과 왕자

왕(King of All Cosmos)이 술에 취해 별을 전부 부쉈다. 5cm 왕자가 지구 물건을 굴려
별을 다시 만든다.

**스토리는 얇게 유지한다.** 이 게임은 스트레스 푸는 쪽이라 화자가 자주 끼어들면
안 된다. 쿨다운 13초. 재촉하는 `idle` 대사는 아예 뺐다 — 그건 이 게임이 주려는
것과 반대다.

농담 구조는 하나뿐이다:

> 왕이 자기 잘못을 왕자 탓으로 굴절시킨다 → 왕자는 말없이 굴린다.

**그래서 왕은 절대 사과하지 않는다.** 대신 말을 돌리거나, 칭찬처럼 들리는 문장 뒤에
지적을 붙이거나, 갑자기 자기 얘기를 한다. 왕이 다정해지는 순간 농담이 죽는다.
결과 화면의 최하위 평가가 "실패"라고 말하지 않는 것도 같은 이유다 —
왕은 실패를 인정하지 않고 실망할 뿐이다.

랜드마크는 쓰지 않는다. 집은 생활 물건의 밀도로 드러나야 한다 —
`generation.ts`의 `LABEL_BUCKETS`가 그래서 원작 실측 크기를 따른다:
도장 2cm · 주사위 2.8cm · 압정 3.1cm · 크레용 3.7~5.9cm · 캐러멜 4.4cm ·
청개구리 7.4cm · 달팽이 9.8cm · 신문 21.5cm · RC 컨트롤러 30.1cm.

대사는 `script.king.ts` 하나에 모여 있고, 엔진(`Narrator.ts`)과 분리되어 있다.
**서울 편에서 왕 편으로 갈아끼울 때 엔진은 한 줄도 안 바뀌었다** —
"도쿄 편은 대본 파일 하나 추가로 끝난다"던 설계가 실제로 값을 했다.

트리거: `start` / `gate`(구역 개방) / `milestone`(지름 2배) / `bigAbsorb` / `impact` / `shed`

## 실제 지형 — 보조 모드

**기본 스테이지가 아니다.** `?district=jamsil` 로만 들어간다.
OSM 실측 도시를 굴리는 경로는 그대로 살아 있고, 아래 도구도 전부 돈다.

```bash
npm run synth-city                      # 합성 잠실 (OSM 없이도 돌아감)
npm run fetch-city -- --preset jamsil   # OSM에서 실제 외곽선
npm run ladder -- --city jamsil         # 크기 사다리에 구멍 검사
npm run citycheck                       # 청크 구성 / 드로우콜 검사
npm run curve -- --donut                # 경계 없는 평지 기준 곡선
npm run dev                             # ?district=jamsil 로 전환
```

프리셋: `jamsil` `gangnam` `seongsu` `hongdae`

아래 절들은 이 보조 모드에 대한 것이다. 집 맵에는 도로도 물도 랜드마크도 없다.

### 왜 서울 전체가 아니라 동네 단위인가

서울은 605km², OSM 건물 60만 채 이상이다. 웹에서 통째로 못 올린다.
그리고 통째로 올려도 재미가 없다 — 5cm 공이 14km 맵에 있으면
첫 1분 동안 반경 20m 안에서만 논다.

동네마다 **사다리 모양이 다르다.** 이게 스테이지 제작의 실제 내용이다.

| 동네 | 예상 특성 |
|---|---|
| 잠실 | 아파트 40~90m + 555m 타워. 상단이 얇다 |
| 강남 | 오피스 위주. 하단(길거리)이 빈약할 수 있다 |
| 성수 | 공장·창고 20~40m. 중간은 좋고 상단이 없다 |
| 홍대 | 저층 밀집. 20m 위로 끊길 가능성 |

`npm run ladder -- --city <slug>` 로 동네마다 확인하고,
끊기면 반경을 넓히거나 목표 크기를 낮추거나 랜드마크를 손으로 넣는다.
**목표 크기를 동네마다 다르게 잡는 게 답일 수 있다** —
홍대는 30m까지 짧게, 잠실은 300m까지 길게.

### 스폰 지점

손으로 찍은 좌표가 호수 안이거나 건물 속일 수 있다.
실제로 잠실 스폰이 석촌호수 한가운데였고, 5cm 공의 카메라 높이(23cm)가
수면보다 낮아 화면이 통째로 물 밑면이 됐다.

- `findClearSpawn()` 이 나선형으로 훑어 물·건물 밖 첫 지점으로 옮긴다
- 수면은 `FrontSide`. `DoubleSide` 면 아래에서 볼 때 벽이 된다
- **길거리 소품은 도시 원점이 아니라 스폰 기준으로 깐다.**
  원점 기준이면 스폰이 멀 때 시작 지점이 텅 빈다

`placeCoef` 는 지역이 넓어도 건드리지 않는다.
2.9배 키웠더니 밀도가 8배 떨어져 첫 흡수까지 5.4m를 굴려야 했다.
넓은 지역은 개수로 채우고 `placeMax` 만 푼다.

### 청크 렌더링

건물을 개별 메시로 그리면 드로우콜이 건물 수만큼 나온다.
420m 격자로 묶어 청크당 메시 하나로 굽고, 흡수되면 그 청크만 다시 굽는다.
색은 vertex color라 머티리얼도 하나다.

합성 잠실 369채 기준 **드로우콜 30개**, 청크당 최대 46채.
실제 OSM(수천 채)을 받으면 `npm run citycheck` 로 다시 재고 `CHUNK` 조정.

### 3층 구조

로그 균등 분포는 도시 **상단에서 성립하지 않는다.**
옥타브당 개수를 일정하게 유지하면 "280~560m 물체 150개"가 생기는데,
실제 서울에 롯데타워는 하나다. 그래서 사다리 꼭대기는 분포가 아니라 손으로 설계한다.

| 층 | 크기 | 출처 |
|---|---|---|
| 길거리 | 1cm ~ 7m | 절차 생성 (`generation.ts`) |
| 건물 | 10m ~ 160m | OSM 실제 외곽선 (`city.<slug>.json`) |
| 랜드마크 | 160m+ | 손배치, 이름·전용 대사 있음 |

마지막 두 번의 "두 배"는 물건 150개를 더 먹는 게 아니라
**정해진 랜드마크 하나를 먹는 사건**이어야 한다.

**집 맵에는 이 층 구조가 없다.** 층이 하나뿐이다 — 1cm~1.2m 소품 1,480개.
벽과 문은 먹으라고 있는 게 아니라서 `ladder` 가 사다리에서 뺀다.
집 맵의 사다리를 나누는 건 크기 층이 아니라 **방**이다.

### 사다리 검사

`npm run ladder` 가 세 층을 합쳐 옥타브별 개수를 센다.
곡선 튜닝(`npm run curve`)이 "얼마나 매끄러운가"를 본다면,
이건 **"애초에 길이 끊기지 않았는가"**를 본다. 이게 먼저다.

특히 두 가지를 잡아낸다:
- 완전히 빈 옥타브 → 플레이어가 그 크기에서 멈춘다
- 길거리 상한과 건물 하한 사이의 이음매 (건물 층이 없는 스테이지에서는 건너뛴다)

**도구가 게임과 다른 월드를 재면 사다리 숫자가 거짓말이 된다.** `ladder` 도 `curve` 도
`CityData.placement` 가 있으면 게임과 **같은 방 목록**으로 물체를 생성한다.
실제로 `curve` 가 이걸 안 하고 있어서, 존재하지도 않는 도넛 월드의 곡선을 보고
"괜찮다"고 말하는 동안 「별을 만들어라 1」이 2초에 끝나고 있었다.

### 건물 크기 = 최대 변

건물의 "크기"는 높이가 아니라 **가로·세로·높이 중 최대**다.
종합운동장은 32m 높이지만 260m 폭이라 사실상 260m짜리 물체다.
높이로만 재면 사다리 중상단에 큰 구멍이 생긴다.

## 성장 곡선 튜닝

```bash
npm run curve                     # 집 맵 — 별 2·4
npm run curve -- --living         # 거실 한 칸 — 별 1
npm run curve -- --town           # 동네 — 별 3·5·8
npm run curve -- --world          # 어친타운 — 별 6·7
npm run curve -- --probe=0.10:12  # 규칙에 없는 판을 미리 재본다 (시작:목표)
npm run curve -- --sweep          # 파라미터 스윕
npm run curve -- --csv            # 원시 데이터
npm run curve -- --donut          # 방 배치 대신 예전 평지 배치로 (OSM 경로 비교용)
```

**재는 맵의 판만 판정한다.** 거실 전용 월드(최대 28cm)에서 별 4(1m)를 재면
당연히 "도달 실패"가 나온다 — 그 맵에 없는 판이라 실패가 아니라 무의미한 숫자다.
**시작 크기가 다르면 곡선도 따로 돈다** — 같은 동네라도 3·5번은 5cm에서,
8번은 10cm에서 시작한다.

`tools/curve.ts`는 렌더 없이 "탐욕적 플레이어"를 시뮬레이션한다 —
가장 가까운 흡수 가능 물체로 직진하고 경로 폭 2R 안의 것은 지나가며 먹는다.
완벽한 플레이 모델은 아니지만 **곡선의 모양**은 정확히 드러난다.

**먼저 볼 숫자는 스테이지 목표 도달 시각이다.** 곡선이 아무리 매끄러워도
제한시간 안에 목표에 못 닿으면 그 스테이지는 클리어가 불가능하다.

```
별을 만들어라 1: 10.0cm 도달 12초 / 제한 무제한
별을 만들어라 2: 20.0cm 도달 27초 / 제한 360초
별을 만들어라 3: 50.0cm 도달 46초 / 제한 480초
```

탐욕 시뮬은 **벽을 모델링하지 않아 낙관적이다.** 실제 플레이는 3~5배 걸린다고 보면 된다.

그 다음이 **CV(두 배 소요시간의 변동계수)**. 낮을수록 매끄럽다.

| 설정 | CV | 비고 |
|---|---|---|
| 초기 (이산 티어 5개) | 0.774 | 서울 월드 |
| 로그 균등 분포 | 0.290 | 서울 월드 |
| 집 맵 (방 배치) | 0.954 | 아래 참고 |

**집 맵의 CV를 쫓지 않는다.** 편차가 큰 건 마지막 구간 하나(86cm → 1.8m,
84초에 1,103개) 때문이고, 그건 큰 공이 작은 것들 위를 지나며 싹쓸이하는 현상이라
원작에도 있다. 무엇보다 **세 스테이지 목표를 전부 지난 뒤**의 구간이다 —
50cm에서 판이 끝나므로 플레이어는 거기 도달하지 못한다.
목표 구간(5~50cm)만 보면 11.8 / 15.6 / 16.8 / 16.8초로 꽤 고르다.
스테이지가 없던 시절에는 CV가 곡선 전체를 대표했지만, 목표가 생긴 뒤로는
**목표까지의 구간**이 봐야 할 숫자다.

게임 안에서는 `T`로 실측 곡선 오버레이를 켠다 (로그 스케일, 점선이 완벽한 지수 성장).
`C`로 CSV를 클립보드에 복사.

스크립트와 게임이 `src/world/generation.ts`와 `src/game/tuning.ts`를 **공유한다.**
파라미터가 렌더 코드 안에 박히면 분석이 거짓말이 되므로 이 분리를 깨지 말 것.

## 부착 디테일

```bash
npm run packing   # 표면 점유 개수 / 겹침량 / 배치 비용 측정
```

물체가 붙어도 안 보이던 문제의 원인은 셋이었다:

1. 중심을 반지름의 82% 지점으로 **끌어당겨** 표면 아래로 넣고 있었다
2. 컬링 기준(`중심거리 < R × 0.92`)이 근거 없는 숫자라 작은 건 붙자마자 증발했다
3. `growth: 3.5` 때문에 공이 자기 껍질보다 빨리 커져 죄다 삼켜졌다

고친 방식:

- **표면에 얹는다.** `dist = R − packRadius × (1 − 2·sink)`.
  sink=0.35면 65%가 밖으로 나온다.
- **완전히 잠긴 것만 숨긴다.** `dist + packRadius < R`.
- **표면을 탄다.** 최근 부착물은 공이 커질 때 같이 밀려나 표면에 남는다.
  오래된 것부터 고정되어 묻히기 시작한다.
  이때 각반경이 줄어들어 새 물체가 사이를 파고들 여지가 생긴다 —
  커질수록 표면이 촘촘해지는 게 이 부수효과다.
- **점유율로 자른다.** 개수가 아니라 표면 점유율(`surfaceCoverage`) 기준.
  작은 공에 110개는 물리적으로 안 들어가고 큰 공에 110개는 휑하다.
  각반경 a인 원뿔의 입체각은 2π(1−cos a)이므로 점유율은 Σ(1−cos a)/2.
- **겹치면 밀어낸다.** 구면 위 완화(Lloyd relaxation의 구면 버전).
  이웃에 대칭적으로 둘러싸이면 힘이 상쇄되어 갇히므로, 갇히면
  무작위 지점에서 재시도하고 침범량이 최소인 결과를 택한다.

| 지표 | 이전 | 지금 |
|---|---|---|
| 표면에 보이는 부착물 (평균) | 25개 | **117개** |
| 겹침 발생 | 2083건 | **822건** |
| 최악 침범률 | 56% | **9%** |
| 배치 비용 | 37µs | 47µs |

## 게임필

- **관성.** 위치를 직접 대입하지 않고 속도를 적분한다. 가속률이 반지름에
  반비례해서 커질수록 묵직해진다.
- **약한 접촉 / 강한 충돌 구분.** 살짝 스치면 벽면을 따라 미끄러지고,
  임계 속도를 넘겨 박으면 튕겨나가며 붙은 게 떨어진다.
  이 구분이 없으면 벽이 미끄러운 유리처럼 느껴진다.
- **떨어진 건 다시 먹을 수 있다.** 구워진 지오메트리는 못 뗀다 —
  깊이 파묻힌 게 안 떨어지는 건 자연스러우니 이 제약이 그대로 규칙이 된다.
- **부착 연출.** 접촉 지점에서 확정 지점까지 0.13초 빨려들어가며 살짝 부푼다.
- **squash & stretch.** pivot과 회전 노드 사이에 스케일 전용 노드를 끼웠다.
  이 노드가 회전하지 않아야 충격 방향이 유지된다.
- **트라우마 흔들림.** 세기를 trauma²로 쓴다. 선형이면 감쇠 끝자락이 질질 끈다.
- **상승하는 흡수음.** 연속으로 먹으면 펜타토닉을 타고 음이 올라간다.
  단발음 반복은 기관총 소리가 된다.

`src/world/generation.ts`의 `GENERATION`:

| 노브 | 효과 |
|---|---|
| `sizeMin/Max` | 크기 범위. 로그 균등 분포 = 옥타브당 개수 일정 |
| `placeCoef` | 월드 전체 크기. 대략 세션 길이에 비례 |
| `placePower` | 배치 반경 = coef × size^power. 곡선 기울기를 좌우 |
| `placeInnerRatio` | 도넛 안쪽 비율. 시작 지점 혼잡도 |

**손배치 스테이지는 위 네 노브를 안 쓴다.** 도넛 공식은 경계 없는 평지를 전제하는데,
벽으로 막힌 방에서는 성립하지 않는다 — 3cm 물체가 3m 밖 복도에 떨어지면 거실에서
먹을 게 모자라 플레이어가 갇힌다. 대신 `stage.house.ts`의 `HOUSE_ROOMS`가
방마다 개수와 크기 범위를 직접 적어둔다. 그게 곧 사다리다.

방 배치에서는 `sizeMax`가 **실제 최대 변**을 뜻한다 (종횡비를 정규화한다).
도넛 배치에서는 종횡비가 곱해져 `size`가 `sizeMax × 1.5`까지 커지는데,
1.8m 복도에 "40cm까지"라고 적어놓고 60cm가 나오면 안 되기 때문이다.

**완화는 경계를 모른다.** `relaxOverlaps` 는 겹친 쌍을 서로 밀 뿐이라 5.4m 거실에
430개를 넣으면 벽을 뚫고 나간다 (실측 1,480개 중 1,250개 이탈). `blocked` 로는 못
막는다 — 벽 **너머** 빈 공간은 "막힌 자리"가 아니다. 그래서 **반복마다** 자기 방으로
접어 넣는다. 마지막에 한 번만 접으면 그 접힘이 새 겹침을 만들고 완화할 기회가 없다.

`new World(scene, seed)`에 시드를 넘기면 같은 월드가 재현된다.

## 알려진 한계

- **동네 맵에 언덕이 없다.** 원작 Pigeon Town은 북쪽 시가지가 언덕 위에 있고
  상점가가 그 언덕을 내려온다. 참새 언덕도, 메추라기 강의 깊이도, 선물이 놓인
  나무와 거기 오르는 미끄럼틀도 평면 엔진으로는 못 만든다. **평면 투영**으로 폈고,
  높이차로 나뉘던 구역은 크기 게이트로 나눴다.
- **동네·어친타운의 개방 문턱과 문 폭은 전부 설계값이다.** 원작의 개방 크기를
  명시한 자료를 못 찾았다. (집 맵의 뒷마당 10cm는 원작 값이라 그건 그대로 뒀다.)
- **어친타운 말고 World가 없다.** 원작 World 맵은 구역이 열넷인데 그중 하나만
  만들었다. 파라다이스·씨브리즈 타운·서커스·고래 도시·큰바다 전부 없다.
- **동네가 원작보다 작다.** 별을 만들어라 8은 원작이 18분인데 우리 동네에서는
  탐욕 시뮬 229초(실플레이 환산 688초)에 12m에 닿는다. 원작 18분은 **원작 크기의
  Town**을 전제한 값이라 그대로 재현되지 않는다. 제한시간은 원작 값을 쓰되
  여유가 크다.
- **동네 랜드마크 5채는 원작에 없는 건물이다.** 6.4m 위 사다리를 잇기 위해 세웠다.
- **동네 상단 사다리가 얇다.** 10~20m 구간에 3채뿐이다(`ladder` 권장 16채).
  간격비는 1.182로 끊기지 않고 목표가 12m라 20m 구간을 채울 이유가 없어서,
  없는 건물을 더 세우지 않았다.
- **2~5번의 시작 크기를 모른다.** 1번(5cm)·6·7번(50cm)·8번(10cm)은 확인됐는데
  2~5번은 어느 자료에도 없다. 지어내지 않고 1번 값을 그대로 뒀다.
- **6번은 무대도 제한시간도 확증도가 낮다.** 무대는 선물 위치로 추정했고,
  제한시간은 10분/11분이 엇갈려 구체적인 쪽(11분)을 택했다.
- **원작 수치를 옮길 때 "최고 평가"와 "목표"를 헷갈리기 쉽다.** 여러 곳에
  "별을 만들어라 5는 2m80cm"라고 나오는데 그건 최고 평가 기준이다 — 같은 출처가
  2번을 "37cm"라 하는데 2번 목표는 20cm다. 5번 목표는 **2m70cm**, 제한은 **13:00**이고
  "8분"은 슈팅스타 조건이다. 옮겨 적기 전에 무슨 수치인지 먼저 본다.
- **지형이 평면뿐이다.** 공의 `y`가 반지름에 고정돼 있어 높이가 다른 구역을 못 만든다.
  그래서 원작 집의 **마루 밑**(20cm 개방) · 다락 · 지붕이 이번 구현에 없다.
  1층 평면만 재현했고, 뒷마당은 같은 평면이라 원작대로 10cm에 열린다.
  경사·계단이 필요해지면 공만 Rapier 리지드바디로 올리고 오브젝트는 지금처럼
  수동 판정을 유지하는 게 낫다.
- 표면을 타는 부착물이 그대로 드로우콜이 된다 (최대 110개 + 구운 것).
  다음 최적화는 이 풀을 InstancedMesh로 돌리는 것 — 매 프레임 행렬을
  갱신해야 하니 애초에 인스턴싱과 궁합이 좋다. HUD의 `draws`로 확인 가능.
- 곡선 후반에서 한 번에 1,000개 넘게 쓸어담는 구간이 있다. 큰 공이 작은 것들
  위를 지나며 싹쓸이하는 건 원작에도 있는 현상이다. 별을 만들어라 8(12m)이
  이 구간을 실제로 지난다.
- **`curve`는 벽을 통과한다.** 구역 개방(`openAt`)은 반영하지만 담장·건물 충돌은
  안 본다 — 직선으로 다음 목표까지 간다. 그래서 "물리적으로 갈 수 있나"는
  도달 범위 검사(flood fill)가 따로 본다. 두 도구가 서로를 못 대신한다.
- 공간 해시 셀이 고정(4m)이라 공이 아주 커지면 조회 셀 수가 O(R²)로 는다.
  반지름에 맞춰 셀 크기를 키우는 계층 그리드가 다음 최적화 지점.
- 구워진 지오메트리는 개별 컬링이 안 된다. 굽기 전에 파묻힌 것만 버리는 것으로
  대충 상쇄하고 있다.
